# Проекция и генерация кода

**Задача:** дать приложению нужные ему типы **WinUI** так, чтобы его единицы
трансляции не разбирали заголовки оригинальной проекции `cppwinrt`. В
официальном C++ стеке от Microsoft
заголовки проекции разбираются заново в каждой единице трансляции, где
упоминается хотя бы один UI-компонент, что приводит к многократному
замедлению компиляции.

## Архитектура и принцип работы

Инструмент кодогенерации `winui-srcgen` (исходный код расположен в
`wxl.gen/`, общие компоненты с визуальным редактором — в `wxl.gen.common/`)
анализирует метаданные `.winmd` из NuGet-пакетов, указанных в активном
профиле, в тех версиях, которые выбрало восстановление NuGet сборки (см.
«Версии пакетов и метаданные Windows» ниже). Генератор строит граф и
вычисляет транзитивное замыкание зависимостей, начиная от заданных корневых
типов; обход идёт в глубину. Список членов у типа ограничивает, куда обход
пойдёт дальше.

Профили — это файлы `<имя>.winxl-profile` в формате JSON с комментариями,
расположенные в каталоге `wxl.gen/profiles/`. Имя в `extends` без
расширения означает файл `<имя>.winxl-profile` в каталоге профиля, который
его называет. Профили построены по принципу последовательного расширения:

| Профиль | Область покрытия и целевое назначение |
| :--- | :--- |
| `base` | Базовый набор элементов управления, эквивалентный WinForms: контейнеры компоновки (layout), текстовые поля, кнопки, списки, индикаторы, навигационные элементы и контекстные меню. |
| `extended` | Современные компоненты **WinUI**, не имеющие прямых аналогов в классическом WinForms: диалоговые и информационные панели, расширенные семейства кнопок, панели команд, меню, пикеры (pickers) и векторные фигуры. |
| `rich` | Графическая подсистема и композиция: визуальные слои (visuals), кисти, тени, анимации, управление полноэкранным режимом и метаданные дисплеев. |
| `full` | Максимальный профиль, включающий все типы, необходимые для сборки и функционирования портированного демонстрационного комплекса [WinUI Gallery](https://github.com/microsoft/WinUI-Gallery) (`samples/Gallery`). |

Вместе с профилями используются вспомогательные конфигурационные файлы:

- `types.json` — декларативная граница кодогенерации: что генератор не
  генерирует, потому что это уже есть в `wxl`. Рукописные базовые типы, на
  которых обход метаданных останавливается (`DependencyObject`,
  `Application`); корни, общие для всех профилей (`Window`); типы WinRT,
  которые `wxl` подменяет своими (`Size`, `Thickness`, `Color`, `TimeSpan` →
  `core::duration`); свойства с собственным тегом (`Margin {20}`) и
  рукописные члены.
- `fluent-symbols.json` — реестр соответствия имён и глифов для шрифта
  пиктограмм Fluent; из него генератор пишет `enum class FluentSymbol`.

### Версии пакетов и метаданные Windows

Профиль описывает только то, что нужно проецировать, и не называет версий,
которые нужно читать. Действующие версии один раз определяет восстановление
NuGet сборки, а генератор получает его результат ключом `--packages`: список
`<сборка>/wxl.packages/restored-packages.json`, который записывает настройка
(см. [«Сборка и верификация»](building.md)). Каждый пакет профиля читается из
каталога и в версии, названных в списке. Метаданные Windows
(`"windowsMetadata": true`) читаются из файлов `.winmd` того Windows SDK, из
которого построена проекция `cppwinrt` сборки, поэтому обёртка и проекция,
которую она вызывает, описывают один и тот же API. Запуск без списка
завершается ошибкой, в которой сказано, где его взять.

Если типам профиля нужен определённый выпуск Windows App SDK, профиль
называет наименьший такой выпуск ключом `minimumWindowsAppSdk`; без этого
ключа профиль версию не ограничивает. Для набора профилей действует
наибольший из минимумов, поэтому профиль, который продолжает `base`, может
повысить требование, но не понизить его. Профиль `full` называет
`2.5.4-experimental`: он проецирует типы, которые объявляет **WinUI** этого
экспериментального выпуска и не объявляет **WinUI** стабильных выпусков 2.5.1
и 2.6.4, — `WrapPanel`, `LayoutPanel`, `FlowLayout`, `PagerControl` и элементы
рукописного ввода (`InkCanvas`, `InkToolbar` и другие). Пакет вне
выпуска (Win2D в `full`) называет наименьшую нужную версию ключом
`minimumVersion`. Версии сравниваются по правилам NuGet.

Генератор останавливается с ошибкой, в которой названы профиль, пакет и обе
версии, если выпуск `Microsoft.WindowsAppSDK` в списке ниже минимума набора
или версия пакета ниже его `minimumVersion`. Если профиль называет пакет,
которого в списке нет, ошибка говорит, что добавить в восстановление сборки.
Тип, который профиль называет, а метаданные восстановленных пакетов не
объявляют, тоже останавливает генератор и редактор: в ошибке перечислены такие
типы, профили, которые их называют, и выпуск `Microsoft.WindowsAppSDK` из
списка, а у каждого типа сказано, что должно его объявить: пакет
восстановления или Windows SDK (тип Windows читается при
`"windowsMetadata": true`); о корне из `types.json` сказано, что его не
объявляют никакие прочитанные метаданные. Ключи `windowsAppSdk`, а у пакета `version` и `overrideVersion`,
генератор не принимает: в сообщении об ошибке названа замена. Ключ, которого
у профиля нет, тоже останавливает генератор.

### Компоненты

Компонент — это каталог `<каталог компонентов>/<имя>/component.json` с
рукописным кодом `wxl.ui`, который вызывает часть проекции, и с описанием того,
что этому коду нужно от проекции:

```json
{
    "name": "window",
    "requires": { "types": { "Microsoft.UI.Xaml.Window": {} }, "windowsMetadata": true },
    "needs": ["elements"],
    "sources": ["window.cpp"],
    "schema": "window.schema.h",
    "surface": "window.surface.cpp",
    "libraries": [],
    "comment": "окно приложения"
}
```

`requires` записывается ключами профиля `types`, `packages` и
`windowsMetadata` и добавляется к корням обхода как ещё один профиль цепочки:
тип, который нужен компоненту, генерируется, даже если ни один профиль его не
называет. Под типом в `requires` компонент объявляет то, что реализует его
рукописный код: синтетические члены (`syntheticMembers`), `fromText` и
`replacedCalls`. Профиль называет типы и их члены, а функции `impl::` и их
заголовки называет компонент, в котором эти функции лежат. Тип без `members` и
`excludeMembers` означает все его члены, поэтому компонент, который только
добавляет типу синтетические члены, пишет `"members": []`: своих членов он не
просит, а члены, которые перечислил профиль, остаются.
`needs` называет другие компоненты, без которых этот не собирается: заголовок,
который компонент включает в кавычках из каталога другого компонента, должен
принадлежать компоненту из замыкания его `needs`. Поэтому компонент, файл
`surface` которого включает `ui.h` или `schema.h`, называет `schema`. `name`
совпадает с именем каталога; ключ, которого у компонента или у его `requires`
нет, останавливает генератор.

`schema` и `surface` называют рукописную часть схемы компонента и её тест —
файлы в каталоге компонента. В `schema` лежат структуры
`wxl::dsl::schema` для классов, которые компонент пишет сам (у эффектов —
`HaloEffect`, `RevealEffect` и остальные, у собственных раскладок —
`AvailableSizeLayout`).
В `surface` лежит единица трансляции, которая проверяет при компиляции каждый
элемент этих структур и синтаксис остальных рукописных классов компонента;
она ничего не выполняет. Запись схемы и её строка в тесте лежат в одном
компоненте и попадают в сборку вместе. Генератор эти два ключа только читает.

Профиль выбирает компоненты ключом `"components": [...]`. Выбранный набор —
объединение `components` по цепочке `extends`, замкнутое по `needs`.

Сборка (функции `wxl_add_ui_library` и `wxl_add_ui_surface_test`,
`cmake/wxl_ui_profile.cmake`) при конфигурации запускает скрипт `cmake/Read-ProfileComponents.ps1` в Windows
PowerShell 5.1: профили и манифесты — JSON с комментариями, а CMake такой JSON
не читает. Скрипт называет компоненты цепочки и для каждого выбранного
компонента — его каталог, исходники, файлы `schema` и `surface` и библиотеки.
Библиотека профиля компилирует эти исходники, а каталог каждого компонента
CMake добавляет к её открытым каталогам включения. Из файлов `schema`
выбранных компонентов сборка составляет `schema.components.h` в каталоге
`<сборка>/wxl.ui/<профиль>` — по одной строке `#include` на компонент — и
переписывает его, только когда набор меняется. Рукописный `schema.h` компонента
`schema` включает сгенерированную схему и этот файл, поэтому в схеме профиля
есть записи только тех рукописных классов, которые профиль собирает. Файлы
`surface` компилируются в цели `wxl.ui.<профиль>.surface-test` вместе со
сгенерированным `parts/schema_surface.cpp`. Такая цель есть у каждого профиля
дерева: у `full` её создаёт `wxl_add_ui_library` рядом с библиотекой, у `base`,
`extended` и `rich`, которые не собирает ни одна программа дерева, —
`wxl_add_ui_surface_test`. Обе функции генерируют обёртки одинаково и дают
цели теста один и тот же открытый интерфейс профиля: каталог сгенерированных
заголовков, каталоги выбранных компонентов и `wxl::ui.common`, без проекции
cppwinrt. Исходники компонентов и части обёрток тест не компилирует, поэтому
профиль, который не собирает ни одна программа, обходится сборке дёшево и
всё же проверяется. Тест `full` компилирует ещё `wxl.ui/test/dsl_surface.cpp` —
проверку синтаксиса на словаре `full`: в нём остаются проверки
сгенерированных классов и того, что пока не отнесено к компоненту, и многие из
этих классов генерирует только `full`.
Манифесты и профили цепочки — зависимости конфигурации: после их правки сборка
конфигурируется заново.

Генератор получает каталоги, в которых ищутся компоненты, ключом
`--component-dir` (ключ можно повторять). Компонент, которого нет ни в одном каталоге,
компонент, найденный в двух каталогах, имя, записанное в другом регистре, чем
имя компонента, имя, повторённое в `components` или в `needs`, и цикл в
`needs` останавливают генератор; в ошибке названы файлы.

Компонент может повторить то, что профиль или другой компонент уже определил
для типа (синтетический член, метод-сеттер, `fromText`, `replacedCalls`), но не
может определить это иначе: тогда генератор останавливается и называет оба
файла.
Тип, который компонент перечисляет без `styles`, не просит ни одного стиля, как
компонент не просит кистей, поэтому стили, сужённые профилем, не расширяются;
тип, который перечисляет только компонент, сохраняет все свои стили.

Ключ `--component <имя>` (его можно повторять) называет компоненты, которые
сборка прочитала из цепочки профилей сама. Если задан `--component-dir`,
генератор сравнивает этот список как множество с `components` цепочки до
замыкания по `needs`; порядок и повторы не важны, а без единого
`--component` список считается пустым. При расхождении генератор
останавливается и называет оба списка. `--component` без `--component-dir`
тоже останавливает генератор: искать компоненты негде.

Заголовок в профиле и в компоненте (`include` и `cppInclude` синтетических
членов, `include` в `fromText` и в `replacedCalls`) записывается так же, как в
`types.json`. Имя с `../` впереди — рукописный заголовок, путь которого
отсчитывается от каталога включения библиотеки: общего `wxl.ui/src` или
каталога компонента. `"../impl/window_helpers.h"` — это файл
`wxl.ui/components/window/impl/window_helpers.h`.
Имя без `../` — файл, который пишет сам генератор (`FluentSymbol.h`). Имя в
угловых скобках — заголовок проекции или стандартный, он пишется как есть и не
проверяется.

Ключ `--common-dir <каталог>` называет каталог включения библиотеки — сейчас
это `wxl.ui/src`. С этим ключом генератор проверяет каждый такой заголовок.
Заголовок с `../` должен быть файлом общего каталога или каталога выбранного
компонента и не выходить за пределы этого каталога; файл компонента, которого
профили не выбрали, не годится, даже если он лежит в общем каталоге. Имя без
`../` должно быть заголовком, который пишет генератор. Иначе генератор
останавливается и называет член, заголовок и файл, который его объявил. Без
`--common-dir` заголовки не проверяются.

В отчёте генератора у каждого компонента перечислены корни, которые добавил
он, а не профиль или компонент раньше него.

### Расширение метаданных (синтетические члены)

Генератор позволяет внедрять функционал, отсутствующий в нативных
метаданных WinRT. Для этого используются три механизма:

1. `syntheticMembers` — объявление синтетических свойств, за которыми
   скрывается рукописная логика библиотеки (например, `Window.MinSize`,
   `Window.Placement`, `UIElement.ToolTip`, `UIElement.Cursor`).
2. `fromText` — функция, которая строит объект класса из строки (`Geometry`
   из текста языка путей XAML).
3. `replacedCalls` — подмена стандартных вызовов платформы своими функциями
   `wxl`.

Обычно все три объявляет компонент, который реализует функцию, — в `requires`
своего манифеста: `Window.MinSize` объявлен в `wxl.ui/components/window`,
`UIElement.ToolTip` — в `wxl.ui/components/elements`. Профиль, выбравший
компонент, получает эти члены вместе с ним. Профиль тоже может объявить такой
член сам, под своей записью типа.

### Структура выходных файлов

Генератор пишет в каталог, который называет ключ `--out`. В дереве его
запускает сама сборка (функции `wxl_add_ui_library` и `wxl_add_ui_surface_test`,
`cmake/wxl_ui_profile.cmake`) и пишет обёртки каждого профиля в каталог сборки,
`<сборка>/wxl.ui/<профиль>/wxl`; родительский каталог — открытый каталог
включения `wxl.ui.full` и каталог включения теста поверхности профиля, поэтому
обёртки подключаются как `<wxl/X.h>`. Чтобы сборка
компилировала заново только изменившееся, файлы перезаписываются только при
изменении их содержимого, а файлы с баннером генератора, которые этот запуск
не написал, удаляются. Рукописные заголовки `wxl.ui` сгенерированный код
называет в угловых скобках путём от каталога включения — `wxl.ui/src` или
каталога компонента (`<Object.h>`, `<impl/conversions.h>`).

Выходная структура распределяется по следующим компонентам:

- **Пространства имён:** для каждого пространства имён (или группы
  пространств, базовые классы которых ссылаются друг на друга) создаются
  заголовки:
  - `<Namespace>.h` — публичные легковесные обёртки.
  - `<Namespace>.impl.h` — приватные цепочки реализации `Impl`.
- **Тела методов:** `parts/wrapper-00.cpp` … `parts/wrapper-<N-1>.cpp` —
  единицы трансляции с реализацией методов всех классов, число которых задаёт
  ключ `--parts` (от 1 до 100, по умолчанию 1; сборка дерева задаёт 8). Части
  берут классы подряд в порядке зависимостей, тела одного класса всегда в
  одной части, а числа классов в частях отличаются не больше чем на один.
  Каждая часть включает заголовки только тех групп, классы которых в ней
  есть. Имена частей известны до запуска генератора, поэтому сборка объявляет
  их результатом своего шага и не читает списков, написанных генератором; одна
  единица на пространство имён сделала бы тела элементов управления
  (`Microsoft.UI.Xaml.Controls`) самой долгой компиляцией дерева.
- **Общие системные файлы:**
  - `PropertyKey.h` и `Members.h` — статические теги и идентификаторы
    свойств и событий.
  - `BindingPairs.h` — пары привязки `isOn = Bind{field}` для классов
    профиля: свойство, которое элемент пишет сам, и события, под которыми он
    это сообщает. Пары перечислены в `types.json` (ключ `bindingPairs`, и
    `boundMembers` для пар с рукописной функцией); пара класса служит его
    наследникам, а тела пар компилируются один раз, рядом с телами класса.
  - `Enums.h`, `Structs.h`, `EventArgs.h` — перечисления, структуры и типы
    аргументов событий.
  - `styles.h` и `brushes.h` — строго типизированные пути к стилям и кистям
    активной темы (генерируются из XAML-словарей ресурсов, которые генератор
    читает через `wxl::xml`).
  - `schema.h` — словарь членов по классам: подсказки IDE и проверка, что
    член принадлежит классу; `parts/schema_surface.cpp` — тест,
    компилирующий каждый его элемент, в цели `wxl.ui.<профиль>.surface-test`.
    Записи рукописных классов добавляют компоненты (ключи `schema` и
    `surface`, см. «Компоненты»).

### Документация в обёртках

С флагом `--docs` генератор переносит в публичные заголовки документацию
метаданных: описание типа, его членов, значений перечислений и полей
структур записывается комментарием `///` перед объявлением, и Doxygen
показывает его на странице обёртки. Источник тот же, что у редактора
профилей: для типов **Windows App SDK** — файл `.xml`, который пакет
поставляет рядом с `.winmd` только на английском языке, для типов Windows —
справочник Windows SDK по контракту типа. Язык справочника задаёт
`--doc-language` именем его папки (список кодов выводит
`winui-srcgen --help`, по умолчанию `en`); другой код генератор отвергает до
начала работы. В дереве оба ключа ставит только генерация для сайта
документации (цель `docs.wrappers`, язык из `WXL_DOC_LANGUAGE`, каталог
`<сборка>/docs/wrappers/wxl`); обёртки, которые компилирует библиотека,
генерируются без них. Код и имя языка для Doxygen генератор записывает в
файл `doc_language.txt` рядом с обёртками, и сайт документации берёт оттуда
язык своих подписей. Если для контракта нет файла на выбранном
языке, используется английский, и генератор сообщает об этом
предупреждением для каждого файла `.winmd`; тем же предупреждением
отмечается `.winmd`, для типов которого документации нет ни на одном языке.
Файл документации, который не удаётся прочитать или разобрать, останавливает
генерацию с ошибкой, в которой названы файл и член. Справочник Windows SDK
берётся той версии, которую называет список восстановления (`windowsSdk`), —
того же Windows SDK, из метаданных которого построены обёртки; справочник
другой установленной версии не читается, как и файл `.xml` рядом с `.winmd`
этого Windows SDK, если он там есть: типы Windows описывает только справочник
на выбранном языке. Описание параметра пишется только
для параметров, которые есть в сигнатуре обёртки, а знаки, которые Doxygen
читает как команды, экранируются. Без флага комментарии не пишутся.

Для интерактивного управления конфигурациями поставляется визуальный
графический редактор профилей — **`wxl.gen.ui`**. Пакеты профиля он берёт так
же, как генератор, — из списка восстановления той сборки, из которой его
запускают, по ключу `--packages`. В дереве его запускает `run-gen-ui.cmd`:
сценарий собирает редактор и передаёт ему список каталога `build/x64-dynamic`. Без
списка редактор показывает ошибку, в которой сказано, как его запустить.

Сгенерированная проекция и обёртки намеренно исключены из репозитория: их
строит сборка дерева в своём каталоге (см.
[«Сборка и верификация»](building.md)).

## Компромиссы и границы применимости

Важно учитывать, что накладные расходы на компиляцию оригинальной проекции
`cppwinrt` не упразднены полностью, а **локализованы внутри самой
библиотеки**: заголовочные файлы `.impl.h` и исходный код обёрток `.cpp`
компилируются лишь однажды — при сборке `wxl.ui`.

Если прикладное приложение запрашивает тип или член **WinUI**, отсутствующий в
текущем сборочном профиле (например, в `full`), компиляция завершится
ошибкой. Для исправления потребуется добавить необходимый элемент в
профиль: следующая сборка сама запустит `winui-srcgen` и скомпилирует то, что
изменилось.

Документация в обёртках покрывает то, что описывают её источники: у пакетов
без файла `.xml` рядом с `.winmd` (Win2D) и у членов, которых в этом файле
нет, комментария не будет. Разметку внутри описаний — картинки, верхние и
нижние индексы, переносы строк, списки, таблицы, жирный шрифт и курсив —
генератор переносит в комментарий, и на сайте она выглядит так же, как в
справочнике Microsoft. Встретив в описании вложенный элемент XML, которого он
не знает, генератор останавливается и называет файл и член.

Подробные сравнительные замеры объёмов заголовочных файлов и выигрыша во
времени компиляции доступны в
[первой статье цикла на Хабре](https://habr.com/ru/articles/1080690/).
